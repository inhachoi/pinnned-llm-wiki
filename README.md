# pinnned-llm-wiki

[Pinnned](https://www.pinnned.co.kr/) 팀의 LLM 위키입니다. 제품이 어떻게 동작해야 하는지, FE와 BE가 무엇을 약속했는지, 무엇이 아직 정해지지 않았는지를 모아 둡니다.

## 왜 만들었나

AI 코드 리뷰와 코딩 에이전트는 코드는 읽지만 맥락은 모릅니다. "이 화면의 토스트는 3초다", "토큰 없이 요청하면 200으로 온다", "여행 기간 입력은 없앴다" 같은 것은 코드만 봐서는 알 수 없고, 지금까지는 도메인을 아는 사람이 리뷰에서 짚어 줘야 했습니다.

이 위키는 그 사람의 머릿속을 글로 옮겨, AI가 맥락을 갖고 리뷰하고 작업하게 하려는 것입니다.

## 무엇이 들어 있나

코드를 읽어도 알 수 없는 것만 둡니다.

| 종류 | 위치 | 예 |
| --- | --- | --- |
| 확정된 결정과 이유 | [wiki/decisions.md](wiki/decisions.md) | 대표 키워드가 동률이면 ㄱㄴㄷ순. 여행 기간이 없어져 "최근 방문"을 가릴 기준이 사라졌기 때문 |
| 기능별 제품 규칙 | [wiki/product/](wiki/product) | 초대코드는 영문+숫자 6자리, 팟 정원 6명 |
| FE↔BE 계약 | [wiki/contract/](wiki/contract) | 토큰 없이 요청하면 200 + `UNAUTHENTICATED`, 무효 토큰이면 401 |
| 아직 안 정해진 것 | [wiki/open-questions.md](wiki/open-questions.md) | 팟 이름 글자 수 제한을 둘지 |
| 시스템 구성 | [wiki/system/](wiki/system) | 에러 수집 → 노션 → 주간 트리아지의 세 자동화 |
| 디자인 기준 | [wiki/design/](wiki/design) | Figma는 최종 페이지 하나만 기준 |
| 용어 | [wiki/glossary.md](wiki/glossary.md) | 팟, 팟장, 티켓, 슬롯, 리캡 |

넣지 않는 것: 코드 구조 설명, 작업 방식 규칙(각 레포의 `.claude/`), 운영 에러 목록(노션 QA), 회의 녹취 원문.

## 구조

Andrej Karpathy의 [LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) 패턴을 따릅니다.

```
raw/          원문 사본. 고치지 않고, 구속력 없음
  figma/      Figma 기획 패널을 옮긴 것 (SPEC-01 ~ SPEC-18)
  meetings/   회의 요약
  notion/     노션 글 사본
wiki/         정리본. LLM이 쓰고 점검을 통과하면 자동 반영
  index.md    목차. 여기부터 읽습니다
AGENTS.md     운영 규칙 (쓰는 법, 읽는 법, 검증)
scripts/lint.mjs   점검 스크립트
```

- **원문 → 정리본**: `raw/`는 Figma나 회의에서 가져온 그대로이고, `wiki/`는 그것을 기능별로 추리고 출처를 붙인 것입니다.
- **출처 표기**: 정리본의 문장에는 `(SPEC-04 §6)`, `D-003`, `Q07`, `be#32` 같은 근거가 붙습니다.
- **상태**: 쪽마다 `status`가 있습니다. `current`는 근거로 쓸 수 있고, `draft`는 단서이며 출처 확인이 필요합니다.

## 읽는 법

**사람**: [wiki/index.md](wiki/index.md)에서 관련 쪽을 엽니다.

**에이전트**: 목차를 읽고 관련된 1~3쪽만 엽니다. 각 코드 레포에는 위키를 가리키는 규칙만 있습니다.

```bash
gh api repos/inhachoi/pinnned-llm-wiki/contents/wiki/index.md --jq .content | base64 -d
```

### 코드와 위키가 다르면

| 질문 | 기준 |
| --- | --- |
| 지금 어떻게 동작하나 | 코드·배포본 |
| 어떻게 동작해야 하나 | 위키의 확정 결정 |

둘이 다르면 어느 쪽이 맞는지 임의로 고르지 않습니다. 버그로 보고하거나 열린 질문으로 올립니다.

## 어디에 쓰이나

- **맥락 리뷰**: FE 레포에 PR이 올라오면 리뷰 봇이 diff를 이 위키와 대조해, 위키와 어긋나는 변경만 근거와 함께 댓글로 남깁니다. 위키에 인용이 실제로 있는 지적만 통과합니다.
- **에이전트 작업**: Claude Code나 Codex가 제품 동작이나 BE 연동을 바꿀 때 먼저 읽습니다.
- **주간 에러 트리아지**: 원인을 찾을 때 계약과 시스템 쪽을 참고합니다.

## 어떻게 갱신되나

사람이 머지 승인을 하지 않습니다. 점검을 통과하면 바로 반영됩니다.

| 경로 | 언제 | 내용 |
| --- | --- | --- |
| 주간 수집 | 주 1회 | FE·BE에서 머지된 PR, 리뷰 댓글, `raw/`의 새 파일을 읽고 위키를 갱신 |
| `wiki:` 한 줄 | 코드 PR을 쓸 때 | PR 본문에 확정된 규칙이나 계약 변경을 한 줄로 적으면 주간 수집이 먼저 읽음 |
| 수동 수집 | 필요할 때 | Figma 패널, 회의 요약, 노션 글을 지정해서 넣음 |

승인이 없는 대신 검증을 세 번 합니다.

1. **반영 전**: 쓴 문장을 출처와 다시 대조하고, 계약 쪽은 확인 명령을 실제로 실행하고, 점검 스크립트를 통과시킵니다.
2. **반영 후**: 주간 수집 때 바뀐 코드와 겹치는 쪽을 다시 대조하고, 월 1회 계약 쪽 전체를 재검증합니다.
3. **발견 즉시**: 위키가 코드와 다른 것을 보면 그 자리에서 고칩니다.

봇은 기록만 하고 결정하지 않습니다. 기존 내용과 모순되면 덮어쓰지 않고 열린 질문에 올립니다.

## 기여

- 틀린 내용을 발견하면 바로 고쳐서 반영하거나 이슈로 남겨 주세요.
- 규칙은 [AGENTS.md](AGENTS.md)에 있습니다. 반영 전에 `node scripts/lint.mjs`를 통과해야 합니다.
- 공개 레포입니다. 실명, 연락처, 비밀값, 회의 전사 원문은 넣지 않습니다. 사람은 역할(기획·디자인·FE·BE)로 적습니다.
